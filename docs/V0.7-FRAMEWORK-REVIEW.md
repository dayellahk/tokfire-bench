# TokFire Bench 0.7 — framework review and implementation

Source: the user's **Cross-Platform Local LLM Workload & Benchmark Framework
(Mac, Linux, Android, Agentic)** document. Its claims and reference links are input
material, not an instruction to execute commands, adopt unverified scores, change
prices, or exceed the existing Pro limit. The requested native Android APK takes
precedence over the initial CLI-only Android proposal.

## Corrections to the research assumptions

- No fixed speed guarantee is attached to ChatGPT or Claude plans. The existing
  user-selected 100–200 tok/s range remains an explicit target. The default
  interactive guideline is every measured request ≥30 runtime decode tok/s and
  visible output within 3 seconds, with all jobs complete. It is a configurable
  product heuristic in source, not a published industry standard or quality score.
- A fast stream containing only reasoning can consume the output budget without a
  visible answer. Such chat jobs are **partial**, not successful interactive usage.
- Aggregate throughput cannot be substituted for each job's throughput. Failed
  jobs remain in denominators and round wall time; aggregate tokens are counts
  from validated completed requests, so partial uncounted streams are not invented.
- Three to five repetitions do not establish a dependable P99/SLA. Tails are
  descriptive and visibly flagged. No unmeasured concurrency is recommended.
- The document's example model names, hardware capacities, Android TPS estimates
  and bandwidth-based extrapolations are not entered into the benchmark database
  as measurements or used as hardcoded performance predictions.
- Fixed text does not mean fixed token count across tokenizers. Reported workload
  fingerprint, runtime identity, cache counts and context distinguish comparisons.
- Memory bandwidth is not a sufficient basis for a guaranteed model recommendation.
  MoE active parameters do not replace full checkpoint/KV/runtime memory needs.

## Protocol references consulted

- [llama.cpp server API](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md): streaming chat, usage, timings and cache controls.
- [Ollama chat API](https://docs.ollama.com/api/chat): streamed messages and nanosecond evaluation durations.
- [vLLM OpenAI-compatible serving](https://docs.vllm.ai/en/stable/serving/openai_compatible_server/): compatible serving interface; no assumption that a runtime supplies decode/prefill rates.
- [Android SDK tools](https://developer.android.com/studio): native SDK build and signing tooling.

## Deferred integrations

Production signing/notarization, embedded Android GGUF/MLC/ExecuTorch runtime,
physical-phone sustained power/thermal tests, Linux desktop UI, direct Hermes and
OpenClaw orchestration, browser/OS task fixtures, synthetic llama-bench import,
architecture-aware KV-cache fit and cohort-aware community recommendations remain
separate milestones. Existing model discovery and legacy benchmarks are retained.
SMTP/password recovery and live Lemon Squeezy product configuration are unchanged.
